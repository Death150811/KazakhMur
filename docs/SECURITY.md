# Безопасность исполнения

Серверный режим Playground принимает произвольный код от пользователей. Этот документ описывает, **что реализовано**,
и **чего нет**. Браузерная версия сайта выполняет код на устройстве посетителя и серверной угрозы не создаёт.

## Статус

| Уровень | Статус |
|---|---|
| Локальный запуск (`qaz run`) | ✅ полный доступ к файлам, как у любой программы пользователя |
| Playground на своей машине / в доверенной сети | ✅ реализованы меры ниже |
| Сайт с браузерным движком (`site/dist/index.html`) | ✅ безопасен для публичного хостинга: код выполняется в браузере посетителя (Worker, лимиты шагов, времени, глубины и вывода), на сервер ничего не отправляется |
| Серверный режим в интернете | ⚠️ **не рекомендуется без контейнерной изоляции** (раздел «Что не реализовано») |

## Что реализовано

**В интерпретаторе (`qaz/interpreter.py`, безопасный режим `safe=True`)**

* Нет `eval`/`exec` для пользовательского кода: исполняется только собственное AST.
* Функции `оқы`, `сақта`, `сыз` отключены (ошибка «недоступна в безопасном режиме»).
* Лимит числа шагов (по умолчанию в Playground — 3 000 000), глубины вызовов (300), времени (3 с)
  и объёма вывода (65 536 символов). Лимиты нельзя поймать конструкцией `байқа`.
* Защита от «бомб»: повторение строк/списков, возведение в большую степень и `аралық` с огромным
  размером не создают гигантских объектов.
* Символьная математика (`шеш`, `туын`, `интегр`): выражение проходит строгую проверку (разрешены
  числа, переменные до 3 символов, арифметика и список функций; нет точек, кавычек, скобок-индексов,
  подчёркиваний) и разбирается SymPy с урезанным пространством имён. Тесты содержат попытки инъекции.

**В бэкенде (`backend/`)**

* Каждый запуск — отдельный процесс `python -m qaz.runner`, а не поток сервера.
* Лимиты ОС (`RLIMIT_CPU`, `RLIMIT_AS` — память, `RLIMIT_FSIZE=0` — нельзя создавать файлы,
  `RLIMIT_NPROC`, `RLIMIT_CORE=0`), собственная группа процессов, жёсткий таймаут с `killpg`.
* Пустое окружение процесса (секреты сервера не передаются), временный рабочий каталог.
* Ограничения размера кода (20 КБ) и ввода (5 КБ), не более 4 одновременных запусков, лимит
  30 запусков в минуту с одного адреса.
* Тесты (`tests/test_backend.py`): бесконечный цикл, бесконечная рекурсия, переполнение вывода,
  «бомба» памяти, доступ к файлам, параллельные запуски.

## Что не реализовано

* **Изоляция файловой системы на уровне ОС.** Процесс запускается от пользователя сервера;
  интерпретатор не даёт доступа к файлам, но защита «в глубину» (chroot, пользовательские
  пространства имён, seccomp) не настроена.
* **Изоляция сети на уровне ОС.** В языке нет сетевых функций, но процесс технически не лишён сети.
* **Квоты на пользователя / аккаунты.** Лимит запросов считается по адресу клиента в памяти одного процесса.
* **Проверка Dockerfile.** `Dockerfile` в репозитории написан по рекомендациям ниже, но в среде
  разработки не было Docker-демона, поэтому образ **не собирался и не проверялся**.

## Рекомендации для публичного размещения

1. Запускать бэкенд в контейнере без привилегий: `--read-only --cap-drop ALL --pids-limit 256
   --memory 1g --security-opt no-new-privileges`, пользователь без прав записи, tmpfs для `/tmp`.
2. Отключить исходящую сеть контейнера (или разрешить только входящую).
3. Для сильной изоляции — gVisor / Firecracker / отдельный runner на каждый запуск.
4. Поставить обратный прокси (TLS, лимиты по IP и размеру тела).
5. Не публиковать Playground, пока не выполнены пункты 1–2 и не проведён собственный аудит.
